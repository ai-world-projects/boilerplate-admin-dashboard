# AVX Admin Platform — Blueprint (for review)

Status: **PROPOSAL — not yet implemented.** This document specifies the target
admin platform (modules, IA, RBAC, approval workflow, and the data contract)
before we build. Review and adjust; implementation follows the phased plan at the
end.

Decisions locked with the owner:

- **Record domain:** generic `Record` (domain-agnostic; rename per project).
- **RBAC:** navigation and routes are permission-gated from the start.
- **Build:** plan first (this doc), then build in phases.

> **Field-naming note (owner request):** entity fields below are patterned on the
> Pinnacle admin conventions and common RBAC/admin APIs so they can be
> cross-checked once the real backend exists. Fields marked **(assumed)** are our
> best guess and should be verified against the real API; the envelope and
> pagination shapes are reused verbatim from Pinnacle and are considered stable.

## 2. Module specifications

### 2.1 Dashboard (`/dashboard`)
- **Stat cards:** Total Users, Active Users, **Pending Approvals**, Records total.
- **Recent Activity** feed (latest audit entries).
- Charts: records-by-status, approvals throughput (approved vs rejected over time).
- Quick link into the Pending Approvals queue.

### 2.2 User Management (`/users`)
- List: searchable, filterable (role, status), paginated.
- **Add User**, **Edit User**, **Activate / Deactivate**, **Assign Role**.
- Show `lastLoginAt`, status chip, role chip.
- Enhancements: bulk activate/deactivate, resend invite, reset password.

### 2.3 Records (`/records`) — generic Content/Record Management
- **View all** with **Search & Filter** (status, owner, date range).
- **View Details** (drawer or `/records/:id`), **Edit**, **Archive** (soft-delete;
  archived records are restorable, never hard-deleted by default).
- A record carries a `status` from the workflow (§5) and an approval history.
- Enhancements: attachments/metadata, version/change history.

### 2.4 Approvals (`/approvals`)
- A **queue view over records** currently needing action by the signed-in user.
- Tabs: **Pending** (mine / all), Approved, Rejected.
- Actions: **Approve**, **Reject**, **Add Remarks** (required on reject).
- Multi-level approvals advance the record to the next level; final approval sets
  `Approved`. Any rejection sets `Rejected` with remarks. All actions are audited.

### 2.5 Audit Log (`/audit`)
- Immutable log: `actor, action, entity, entityId, before/after, timestamp, ip`.
- Filter by actor, action type, entity, date range.
- **Admin Activity** = the same log filtered to admin-role actors.

### 2.6 Notifications (`/notifications`)
- In-app center: read/unread, mark-all-read.
- Generated by workflow events (assigned an approval, your record approved/rejected).
- Header bell shows unread count.

### 2.7 Reports (`/reports`)
- **Summary** dashboards (users, records by status, approval turnaround).
- **Export** to **CSV and PDF** for each summary.

### 2.8 System Settings
- **Access (RBAC)** — manage Roles, the Permission matrix, and role assignments.
- **Workflow** — define **Statuses**, **Approval levels**, and **Approvers** per level.
- **Security** — **Password rules**, **Session timeout**, **Account lockout**.
- **Branding** — **Brand icon / logo**, app name, primary color.

### 2.9 My Profile (`/profile`)
- Change own password, manage 2FA (later), view own roles/permissions.

## 3. Entity data contract

Envelope (stable, from Pinnacle): `StandardResponse<T> = { result, message, data }`.
Pagination (stable): `Paginated<T> = { total, page, limit, totalPages, data }`.
All list endpoints accept `keyword?, page?, limit?` plus per-module filters.

### 3.1 User
```ts
interface User {
  _id: string;
  firstName: string;
  lastName: string;
  email: string;
  roleIds: string[];          // many-to-many with Role (users can hold multiple roles)
  status: 'active' | 'inactive' | 'pending';  // includes Pending Approval
  lastLoginAt: string | null; // (assumed)
  createdAt: string;
  updatedAt: string;
}
```

### 3.2 Role & Permission (RBAC)
```ts
interface Role {
  _id: string;
  name: string;               // e.g. "Approver"
  description: string;
  permissions: string[];      // permission keys, e.g. "records:approve"
  isSystem: boolean;          // (assumed) system roles can't be deleted
  createdAt: string;
  updatedAt: string;
}

interface Permission {        // usually a static catalogue, not CRUD
  key: string;                // "resource:action"
  label: string;
  group: string;              // "Users" | "Records" | ...
}
```

### 3.3 Record (generic)
```ts
interface Record {
  _id: string;
  title: string;
  description: string;
  status: string;             // references a workflow Status (§5)
  ownerId: string;            // (assumed) user who created it
  ownerName: string;          // (assumed) denormalized for list display
  currentApprovalLevel: number; // (assumed) 0-based index into workflow levels
  attachments: Attachment[];    // API returns file URLs (see Attachment)
  isArchived: boolean;
  createdAt: string;
  updatedAt: string;
}

interface Attachment {
  _id: string;
  fileName: string;
  fileUrl: string;              // absolute URL returned by the API (mock uses placeholder URLs)
  mimeType: string;            // (assumed)
  sizeBytes: number;           // (assumed)
  uploadedAt: string;
}

interface ApprovalAction {    // history entry on a record
  _id: string;
  recordId: string;
  actorId: string;
  actorName: string;          // (assumed) denormalized
  level: number;
  action: 'submit' | 'approve' | 'reject';
  remarks: string;
  createdAt: string;
}
```

### 3.4 Audit log
```ts
interface AuditEntry {
  _id: string;

  actorName: string;          // (assumed) denormalized
  action: string;             // "user.create", "record.approve", ...
  entity: string;             // "User" | "Record" | ...
  entityId: string;
  before: unknown | null;     // (assumed) snapshot
  after: unknown | null;      // (assumed) snapshot
  ip: string;                 // (assumed)
  createdAt: string;
}
```

### 3.5 Notification
```ts
interface Notification {
  _id: string;

  type: string;               // "approval.assigned" | "record.approved" | ...

  link: string | null;        // (assumed) deep link, e.g. /records/:id

}
```

## 4. RBAC model & gating

- **Permission key format:** `resource:action` (e.g. `users:read`, `records:approve`,
  `settings:rbac`). The full catalogue lives in `src/auth/permissions.ts`.
- **Default roles (seed):** Super Admin (all), Admin, Approver, Editor, Viewer.
- **Current user + permissions** are loaded once (`GET /auth/me`) into an auth
  context/store; a `useAuth()` hook exposes `hasPermission(key)`.
- **Gating layers:**
  1. **Sidebar** — items/groups filtered by `hasPermission`.
  2. **Routes** — a guard component redirects to a 403 page if the permission is
     missing (defense in depth; menu hiding alone is not security).
  3. **UI affordances** — action buttons (Approve, Delete, etc.) hidden/disabled
     without the permission.
- The mock signs you in as **Super Admin** so every screen is reachable in dev.

## 5. Approval workflow (state machine)

Default statuses (configurable in Workflow Settings):

```
Draft ──submit──▶ Pending ──approve(final level)──▶ Approved
                    │
                    ├─approve(non-final)──▶ Pending (next level)
                    └─reject──▶ Rejected   (remarks required)

Any status ──archive──▶ Archived (restorable)
```

- **Approval levels** are ordered; each level lists approver role(s). A record in
  `Pending` shows to approvers whose role matches `currentApprovalLevel`.
- Approving a non-final level increments `currentApprovalLevel`; approving the
  final level sets `Approved`. Rejecting sets `Rejected` and stores remarks.
- Every transition writes an `ApprovalAction` (record history) **and** an
  `AuditEntry`, and fires a `Notification`.

## 6. Impact on the current codebase

Additions (new): `src/auth/` (permissions catalogue, `useAuth`, `PermissionGate`,
guard), feature folders `records/ approvals/ roles/ audit/ notifications/
reports/ settings/`, matching `api/services/*` + `api/interfaces/*`, and MSW
handlers/data per module.

Changes: replace the `subjects` feature/page with generic `records`; expand
`navConfig` into grouped, permission-tagged items; render the sidebar and routes
through the permission gate; branding settings feed the theme's CSS variables.

Reused as-is: axios client + interceptors, `StandardResponse`/`Paginated`,
TanStack Query + RHF/Zod patterns, and all `AVX*` components (they already cover
tables, drawers, dialogs, search, headers, stat cards).

## 7. Phased build plan

1. **Foundation:** auth context + `GET /auth/me` mock, permissions catalogue,
   `PermissionGate` + route guard, grouped permission-gated nav, 403 page.
2. **Users + RBAC:** users CRUD w/ status + role assignment; Roles CRUD +
   permission matrix.
3. **Records + Approvals + Workflow statuses:** records CRUD/archive, approval
   queue + approve/reject/remarks, record history, workflow-driven statuses.
4. **Audit + Notifications:** audit log (+ admin filter), notification center + bell.
5. **Reports + Settings:** summary + CSV export; Security + Branding settings.

---

## 8. Resolved decisions

1. **Roles per user:** multiple (`roleIds: string[]`).
2. **Record attachments:** yes in v1; the API returns file URLs (`Attachment.fileUrl`);
   the mock uses placeholder URLs.
3. **Approval levels:** fully admin-configurable from day one (Workflow Settings).
4. **Reports export:** CSV **and** PDF.
5. **2FA:** deferred (Profile ships without it for now).
